# Shared res contract (v1.10, 2026-11-18) - owner: routing/global-rules orchestrator; users: all projects

Maintained source: this project-orchestrator repository, `scripts/res/res`. Ownership of the entire
tool (devices, checkouts, registry/notes, take/return/extend/add/note/log and heavy admission) transferred
from vesdk-mainline to the global-rules owner on 2026-11-13. The unmodified v1.2 contract is preserved
in `scripts/res/test/fixtures/contract-v1.2.md`. v1.10 takes effect at the owner's reviewed switch.

## Rebuild-aware runner extension (BC-135–137)

`wait-pool --placement-file JSON` consumes the runner's atomically refreshed
version-1 slot scores, not a lease grant. It selects the minimum remaining wait
plus rebuild time while retaining FIFO and all hard admission checks. A missing
non-rebuildable input is hard ineligibility. Placement tables are emitted once
per minute or when the chosen slot changes. A placement snapshot older than
180 seconds fails closed. Runner settings are documented in devbox-run.md.

`take`/`wait-pool --maintenance` on a devbox slot bypasses only the disk gate and
sets disk cost to zero. This lets GC free space when disks are below 53 GiB;
load, memory, policy and registered row limits remain binding. Normal runs still
preserve the real-space floor. `--extra-disk-gib` adds declared new content to the
configured/per-slot workspace budget.

New reservation records are `[at, cores, memoryGiB, diskGiB, owner]`; owner has
`slot`, `by`, `pid`, `host`, `start`. Reads discard expired/mismatched owners and
deduplicate by slot. Return/reclaim removes the exact owner under the host ledger
lock; acquisition rollback does the same if it published a reservation. Anonymous
legacy three/four-field records remain TTL-bounded until owner rollout archives
them. Quiesce devbox admissions, coordinate all active holders' return, back up
and archive the old ledgers, then publish the matched controller/runner. Do not
archive while old live admissions still need their budget protection.

## Changes in v1.10

- `wait-pool` treats `--exclude-host` and `--exclude-slot` as soft unless the caller supplies `--exclude-reason TEXT`. `DEVBOX_SOFT_EXCLUDE_MINUTES=5` sets the minimum per-wait age. If no allowed matching slot is free and gate-admitted and an excluded matching slot is, the controller announces the available hosts and exposes `self_restricted` and the reason in `res status`. After the threshold, it drops all soft exclusions for that wait without losing its FIFO position, and emits `softExclusionsDropped=<JSON>` on stdout and a journal entry. It still obeys normal FIFO and gate checks. Explicit internal `--hard-exclude-host` and `--hard-exclude-slot`, policy, capability and quarantine checks never loosen. Preferences affect order only.
- An armed owning worker watcher emits one `pool-stalled` alert per reasoned wait over 10 minutes with a current `self_restricted` diagnosis. The alert includes the holder, task, reason and available hosts. Ownership uses the worker thread/account or an explicit owner and unique matching task.
- Enrolled hosts require `freeGiB - reserved_disk_gib - task_disk_gib >= 53`, including when the FIFO load override is active. Each admission reserves disk for 15 minutes, ending immediately on return or stale reclaim (and otherwise expiring after 15 minutes, including stale-metrics fallback), independent of the five-minute CPU and memory budgets. All three budgets end on return; each live slot ownership has at most one reservation. `--disk-gib N` overrides disk cost (zero allowed); `--disk-gib-file JSON` supplies per-slot costs. The runner sends zero for an existing project worktree and configured cost for a new one; direct takes retain configured defaults. The 53 GiB real-space floor still applies. Legacy anonymous ledgers expire at their original TTL and cannot be attributed to a holder. `DEVBOX_HEAVY_DISK_GIB=20` and `DEVBOX_LIGHT_DISK_GIB=2` accept `.<host>` overrides and `.project.<slug>` overrides. Project values take precedence over host values. Missing, invalid or stale `freeGiB` uses the existing static fallback. Status and the admission journal show free and reserved disk. The metrics sampler uses the workspace-root filesystem. Existing runner disk checks and garbage collection retain their thresholds.
- `res retain-remote <id> --by <holder> --pid <holder-pid>` marks a matching locally owned devbox hold as requiring confirmed remote cleanup. A marked light hold stays out of automatic stale reclaim. It remains visible and the owner can return it after confirming cleanup.

For the owner switch, back up the current executable and machine configuration, then stage and atomically rename the new executable and any config updates in the shared directory. Keep the current host enrollment and registry. Publish the runner and watcher from the same revision and re-arm active owner watches. Before rolling back to v1.9, quiesce devbox admissions, disable dynamic admission and atomically restore the previous configuration without the new keys. Archive the v1.10 reservation JSON ledgers before enabling dynamic admission on v1.9, which only understands three/four-field entries. Wait 15 minutes after the last v1.10 admission before archiving if outstanding disk reservations still matter. Resolve marked retained light holds before restoring a controller that cannot recognize the marker.

## Changes in v1.9

- Enrolled CN hosts gate new numbered heavy and light slot claims using Linux's **5-minute load average** and `MemAvailable`. Admit if `load5 + reserved cores + task cores <= cores × load-per-core` and `MemAvailable - reserved GiB - task GiB >= memory floor`. A per-host guard shares the reservation budget between both pools and direct takes. Each admitted start reserves its estimated cost for five minutes, including starts that used static fallback and runs that have already returned. The registered open rows remain the hard cap.
- Default `machine.conf` keys are `DEVBOX_LOAD_PER_CORE=1`, `DEVBOX_MIN_AVAIL_GIB=4`, `DEVBOX_HEAVY_CORES=3`, `DEVBOX_HEAVY_GIB=4`, `DEVBOX_LIGHT_CORES=1`, and `DEVBOX_LIGHT_GIB=2`. Append `.<host>` to any of these six keys for a per-host override, for example `DEVBOX_HEAVY_CORES.10.37.121.175=3`. Enable with `DEVBOX_DYNAMIC_ADMISSION=1` and `DEVBOX_DYNAMIC_HOSTS=10.37.121.175,10.199.23.45,10.199.23.46`. Set the switch to `0` to restore static admission immediately without evicting holders. Publish changes with a sibling temporary file and rename.
- `res` reads `devbox-metrics/<host>.json` locally. Missing, invalid, future-dated or at least five-minute-old samples trigger static admission on that host. An open row tagged `dynamic-only` requires both enrollment and a fresh sample. The rollout marks `devbox-cn-3` and `devbox-cn-4` this way so CN1 keeps its two baseline heavy rows on fallback or shutdown. Back up `resources.tsv` to `resources.tsv.before-dynamic` before opening and tagging those rows. Install the controller before publishing the registry changes and coordinate old waiters before opening the floating rows.
- On measured hosts, queued callers preserve headroom on each host an older compatible waiter can use. A FIFO head observed load-blocked for 20 minutes may bypass the load check for its one acquisition. It still needs available memory, an open compatible row, and all normal runner disk checks. Direct takes and younger waiters have no load override. Gate refusals from direct takes return 2 for load/memory and 3 for closed floating rows. Pool waits continue to their normal timeout or another eligible host.
- `res status` shows each host's held/open row counts and `gate=OPEN|CLOSED` for heavy and light with the reason, load5, reserved cores/GiB and available memory. It reports actual holds even if the switch or metrics have since closed a floating row. `log.tsv` records `gate-admit` and `gate-deny` for evaluated dynamic decisions with the same readings and a reason, including `load-override` and static fallback. The runner collects the sample and checks disk space on the host.
- `DEVBOX_LIGHT_STALE_RECLAIM=1` independently opts in to automatic reclaim on `devbox-cn-light`. Only that pool's FIFO head may reclaim an otherwise eligible slot whose hold is strictly older than 15 minutes and whose recorded PID is proven dead on the local `res` host. Admission still applies normal policy, capability, quarantine and any configured load/memory gates. The default and kill switch are `DEVBOX_LIGHT_STALE_RECLAIM=0`. Status shows stale light holds and their reclaim eligibility. A `reclaim-stale` journal entry names the previous holder, which also appears in status while a replacement hold remains active. Heavy devbox holds require the existing manual return and leave other free slots available to the FIFO head.

## Changes in v1.8

Normal lanes 1/2 now require load1m <=1.25 x physical cores and memorystatus available memory >=12 GiB.
Full builds use a counted `heavy-build` resource (default two, configurable 1..3): the first holder also
requires load1m <=1.5 x cores, while later holders require load1m <=0.6 x cores, >=24 GiB available,
and a checkout/repository identity distinct from every active build. A legacy holder without identity
metadata blocks concurrent admission. Selection is serialized by the private build-admission lock, but
each build still holds one lane and never holds either half while waiting for the other. The blocking FIFO
head may bypass only the new first-holder/lane-1/2 gates after 20 minutes; legacy, concurrent, lane-3,
metrics, occupancy and FIFO checks remain mandatory. Status reports `heavy-build k/N`; return telemetry
records solo/concurrent mode, peak concurrency and duration for fleet comparison. All new gates, the
15..30-second load poll, concurrency cap and override age accept validated `machine.conf` overrides.

## Changes in v1.7

Fresh build/lane transactions cannot adopt a pre-existing hold, including a concurrent wrapper's
same-name hold that appears after the free-directory precheck. They return unavailable or keep waiting,
and roll back only their newly created resources. Same-`--by` single-resource take/wait idempotence
is unchanged, as is `wait-lane` reuse with the same `--by` and holder PID. Holder names remain opaque,
exact strings; no prefix or project/task comparison establishes ownership. Existing-hold diagnostics
from `take` and the same-name build-slot guard name the recorded holder, PID and since time instead
of calling the hold "yours". A shared `--by`
alone cannot identify a wrapper: keep using unique names per run and PID-scoped `return-build` cleanup.
Admission, FIFO, release authorization and the strictly >600-second dead-local-PID reclaim rule are unchanged.

## Changes in v1.6

Lane waits publish the same heartbeat and cleanup records as build waits. While another project
has a live, ready lane waiter and no non-STALE lane, a project holding a lane cannot take an additional one. Eligible
lane waiters proceed FIFO; capped projects yield queue position, and three gate-blocked polls
suspend priority until the next passing poll. Build waiters retain v1.5 priority. Status lists
waiting lanes. Machine gates accept validated optional `machine.conf` overrides. Device holds
and take logs retain adb line counts and adb/devicectl process identities. Review timing rejects
older released episodes when a later held snapshot reuses a name/PID, and marks inconsistent
release/acquisition bounds INVALID with unknown durations only when the release window proves the timing impossible; valid same-minute episodes retain coarse bounds. Review version labels come from this
source contract; they do not establish the installed version.

Resources in `res` (~/.claude/orchestrator/_shared/res):
- `heavy-build` — counted machine-wide full-package build capacity; one logical registry row is backed by internal `heavy-build`, `heavy-build-2` and `heavy-build-3` holds up to the configured 1..3 cap (default 2).
- `heavy-lane-1`, `heavy-lane-2` - the two normal heavy-task lanes.
- `heavy-lane-3` - optional third heavy-task lane; default admission requires load1m <=8 AND available memory >=32 GiB at take time (see machine overrides below). Capacity floats between two and three lanes, not an automatic tuning range for load/memory.

Definitions:
- Full-package build = a full iOS or Android SDK+host-app build: an env verify run (preflight, stage, compile, acceptance), an xcodebuild of the app, a Gradle assemble with native compile. Needs one counted `heavy-build` hold AND one lane, held for the whole run.
- Heavy task = full-package build, SG packaging, a heavy focused test that compiles native code or runs many processes for a sustained period. Needs one lane.
- Remote dev machines (user 2026-11-16, "开发机上不占用 mini 的资源"): a step that executes ON a devbox (render/export, Docker image build, SG image checks, slow suites) is NOT a mini heavy task: it never takes `heavy-build`, a `heavy-lane-*` or `--shared-lock`, and is not subject to `heavy-check`. The mini side (ssh, `git archive | ssh tar`, polling) is light. Devbox capacity is coordinated with machine-scoped `remote` resources shared by all projects. Use `res wait-pool devbox-cn --by <unique wrapper id> --project <slug> --task <task> --for "<step>" --pid <long-lived wrapper pid> --timeout <min>` for heavy steps. It selects any registered `remote` row named `devbox-cn-<number>` (including newly added slots), excluding light slots. Success prints `slot=<id>`: capture that ID, hold only around the remote step, then `res return <id> --by <unique wrapper id>`. Checks under ~5 min use `res wait-pool devbox-cn-light`, which selects `devbox-cn-light` or `devbox-cn-light-<n>`. Each pool has a FIFO queue shown by `res status`, with heartbeat/rejoin and cleanup on signals or timeout. Re-waiting with the same holder/PID/host returns its existing pool slot without changing the hold. A trailing hyphen in the prefix is optional and uses the same queue. No mini resource or heavy gate is acquired. Slots: devbox-cn-1..4 + devbox-cn-light on CN devbox 1 (10.37.121.175, 8 cores/32 GiB; one heavy e2e ≈ 2.5 cores/<3 GiB), devbox-cn-5..6 + devbox-cn-light-2 on CN devbox 2 (10.37.249.249, 8 cores/15 GiB). Devbox ssh always names the devbox account: `ssh wangsiyu.chris@<ip>` (a bare `ssh <ip>` logs in as the local user `bytedance` and fails with "Permission denied (gssapi-with-mic)" even with a valid ticket; BC-87). Remote wrapper standard (BC-83, 2026-11-17): ssh with `-o ServerAliveInterval=15 -o ServerAliveCountMax=4` and one retry on "message authentication code incorrect"/"Corrupted MAC"; run remote steps in their own process group with a pidfile (`setsid`), and on every exit kill that group and confirm it is gone BEFORE `res return` of the slot; a remote owner that acts as a subreaper must reap adopted children continuously while it runs (not only at shutdown), excluding its own Popen children, or zombies make liveness checks lie. SG devbox: none right now (10.199.196.191 retired 2026-11-17, the user is replacing it with a bigger one; `devbox-sg-light` is policy never). A new devbox gets a new res slot only after the rules owner checks ssh as wangsiyu.chris, host fingerprint, cores/RAM/disk and tools. Company remote build services (RemoteX), remote pipelines and CI run on their own capacity: no devbox slot and no mini lock (user 2026-11-16, "remoteX 构建也不需要占 devbox 槽位"); only compile steps that still run on the mini take heavy-build. Access is the user's normal ssh (Kerberos); an ssh auth error is BLOCKED, workers never kinit. Only code and demo/synthetic media go to devboxes: no secrets, no user or colleague media.
- NOT heavy: host unit tests that don't run a full native compile, single-TU compiles, doc/analysis work, device sessions without builds. Commands (existing single-resource semantics unchanged except the documented PID diagnostics):
- Remote pool health: `res box-health [--json]` reads `<RES_DIR>/box-health.json` without probing. Hosts are parsed from `user@host` in remote resource descriptions. `res quarantine <host> --reason "..."` excludes every slot on that registered box until `res unquarantine <host>` clears quarantine and failure history. `res report-infra <slot> --kind ssh|disk|upload` records a box-level infrastructure failure. Three failures in a rolling 30-minute window quarantine the box for 20 minutes; expiry automatically allows selection again. After an automatic quarantine, the next infrastructure failure starts another 20 minutes even if the old failure window has expired; a good runner probe may call `unquarantine` to reset this history. Manual quarantine remains in force until explicitly cleared. State writes are serialized and atomically published; malformed health state fails pool selection. Disk, SSH and load probes belong to the runner, not res. Existing holds remain owned and can be returned normally.
- Soft placement tags and exclusions: `prefer=vesdk-android,android` raises a slot ahead of untagged slots when `--need` includes either name. For other requests it ranks after untagged slots, so generic work can use it when the other eligible slots are busy. All required capabilities, open policy, quarantine and exclusions still apply. Affinity and capacity order candidates within each tier as described below. `--exclude-slot <id>[,<id>]` and `--exclude-host <ip>[,<ip>]` initially remove candidates before ranking, subject to the v1.10 fallback above. FIFO protects scarce overlapping capacity; a queued waiter may use surplus capacity as described below.
- Remote pool capabilities and affinity: add `caps=node,android-vesdk,...` tags per slot description; slots on the same box may advertise different capabilities. `res wait-pool <prefix> ... --need <cap>[,<cap>]` requires every named capability, keeps FIFO, and fails immediately if no open member has all requested tags. A compatible quarantined or occupied member remains a bounded wait. `--prefer-host <ip>` prefers a free eligible slot there and immediately falls back elsewhere. `--prefer-slot <id>` first prefers that free eligible member, then other members on its host, then the explicit preferred host (if any), then any eligible member. Preferences never override capabilities, quarantine, open policy or FIFO. A named preference may be missing or busy; it does not delay fallback. Membership/health is refreshed each retry and checked again after reservation. Reusing a hold requires the same holder/PID/local host and a member compatible with the current `--need`; quarantine does not revoke a hold. These options acquire no mini resource.
- **Capacity-aware placement.** Within each `prefer=<cap>` tier, rank by preferred slot, that slot's host, explicit preferred host, then ascending `(held slots on host + 1) / cores`, most recent same-repo slot use, descending cached `freeGiB`, and slot id. Affinity applies only when the host's post-take score is at most 0.5. Count all registered remote holds on the host, including light slots and slots outside the requested pool. Read `cores` and `freeGiB` from `devbox-hosts.json` when its timezone-qualified `probedAt` is at most 24 hours old and in the past. If core data is unavailable, use the first valid positive integer `cores=` tag on that host, then 8. Unknown free space ranks as zero. `res status` and `res box-health` show `heldSlots`, `cores`, current `score=heldSlots/cores` and post-take `nextScore`. `box-health --json` also exposes nullable `freeGiB`. Slot-filtered status shows the selected slot's host.
- **Warm-slot ties.** The optional `devbox-affinity.json` uses devbox-run's `<repo identity>+<branch/ref>` keys and `{host, slot, time}` values. The identity is `id-<sha256(project:<project>)>` or the `id-<64 hex digits>` identity passed by a runner without an explicit project. For the same repository across branches, a more recently used slot wins a capacity-score tie. Ignore other repositories, host/slot mismatches and records with invalid or future timestamps. Absent or malformed caches fall back to the remaining tie-breaks.
- **Surplus-aware FIFO.** A queued caller may take a slot if it leaves the same maximum allocation available to older live waiters. Compute that allocation from current free, open, healthy members and each older waiter's capabilities and exclusions. A still-queued waiter with a compatible claim from its own controller already has a slot. A short per-pool filesystem guard keeps claim metadata and mkdir visible together, then releases before post-claim validation. Recheck against the latest registry, health and waiters after mkdir. Plain remote takes continue to honor the pool reservation.
- **Rollback and requeue.** Identify the current waiter by its directory or the exact order, holder, PID and host tuple. Refresh its heartbeat before attempting a claim and before the post-claim FIFO check. Rejoin an expired or deleted waiter with its original order. After three fresh claim rollbacks in one pass, move the waiter behind those already queued and log `waiter-yield`. Keep its original start and timeout. A busy slot that produced no claim does not count as a rollback.
- **Exec-light admission.** Each pool attempt, plain remote take or return, and status without device probes runs one Python invocation. The interpreter uses the registry, local lock directories, cached health and waiter metadata. It performs no SSH or subprocess probes. Backoff sleeps inside the interpreter. The wrapper forwards INT, TERM and HUP and protects cleanup from repeated signals. The heartbeat TTL defaults to 300 seconds and accepts the `RES_WAITER_STALE_SECONDS` override. The hidden `.episode.*` record preserves order and start across waiter deletion and rejoin. Normal completion, timeout or cancellation removes it.
- Fleet reporting: `node scripts/fleet-report.mjs [--since <ISO>|--hours N] [--json]` defaults to 24 hours and reads `RES_DIR`, then `RULES_SHARED`, then the normal shared directory. It replays the full `log.tsv` with `resources.tsv` to pair pre-window holds and waiter starts. It reports per-resource and per-box reserved slot-hours, busy/idle percentages, takes, nearest-rank wait p50/p90/max, current holders, mini/devbox totals, and solo versus concurrent build-duration p50/p90/max. Successful `waiter-start` → `waiter-acquire` pairs determine queue waits; timeout/rejoin records do not count as acquisitions. Build duration samples come only from well-formed return details containing `build_mode`, `peak_concurrent` and `duration_seconds`. The current lock snapshot supplies holders when available. Mini compute totals count lanes, excluding the overlapping counted build capacity. Box/totals denominators use currently open slots over the full window: registry history and CPU usage are not inferred. A box idle over 70% in 09:00–21:00 PST (fixed UTC−08:00, every day) gets a move-work/reduce-slots suggestion; pool p90 over 10 minutes gets an add-slots/move-work suggestion. Unzoned journal times use the collector's local timezone. Optional `devbox-hosts.json` is keyed by IP with `freeGiB` and ISO UTC `probedAt`; absent fields show unknown, and probes older than 24 hours are marked stale. This report never probes or writes shared state. `status.mjs` text includes one line per box; nightly review collects text and JSON reports. Its existing status JSON format is unchanged.
- Full build, one attempt: `res take-build --by <session> --project <slug> --for "<purpose>" --task <id> [--pid <pid>] [--lane heavy-lane-1|heavy-lane-2|heavy-lane-3] [--checkout <path|resource>]` → 0 pair acquired, 2 unavailable, 5 overloaded, 1 usage/metrics error. `--checkout` is optional; otherwise admission infers owned checkout locks, the current Git common directory without invoking Git, then project identity.
- Full build, bounded: `res wait-build` with the same flags and required `--timeout <minutes>` → 0 acquired, 2 timeout; other errors propagate. Acquires one admitted counted build hold AND the first free admitted lane (1, 2, then optional 3), or holds neither before every retry. `--lane` pins a lane without hold-and-wait. The first build adds the per-core first-holder gate; later builds use the stricter concurrent load/memory gate and distinct checkout/repository identity. Both commands retain the legacy heavy gate; lane 3 also checks its stricter gate at acquisition.
- Heavy task, any lane: `res wait-lane --by <session> --project <slug> --for "<purpose>" --task <id> [--pid <pid>] --timeout <minutes>` → selects 1, 2, then 3 if registered and OPEN, without taking `heavy-build`. Repeating it with the same `--by` and holder PID returns the caller's existing lane instead of consuming a second lane.
- Pair release: `res return-build --by <session> [--pid <holder-pid>] [--note "<text>"]` → returns that unique holder’s lanes (3/2/1) before its owned counted build hold; leaves other holders untouched. Optional --pid limits release to that recorded holder PID; the build wrapper uses this to protect preexisting same-name holds. The normal returns also work. Use a unique `--by` for each run, never share it with concurrent heavy tasks or nest/adopt an existing build hold. Success ends with `build-lane=<id>` or `lane=<id>` so a wrapper can capture the selected lane. New command help: `res take-build --help` (legacy help remains byte-preserved).
- Build-waiter fairness (v1.5, extended v1.8): every blocking `wait-build` (including `take-build --wait` callers that map to it) publishes holder/project/task/PID/host/start plus a heartbeat refreshed on each poll. The record is removed on acquire, timeout, INT/TERM/HUP and ordinary exit. Records with a dead local PID or a heartbeat older than 45 seconds (about three maximum poll intervals) are ignored and cleaned. `res status` lists live waiting builds with holder, start time and current blocker (`load`, `gate`, `slot`, `lane` or `FIFO`); only the FIFO head may accumulate the v1.8 load-override timer. The log records `waiter-start`, `waiter-acquire`, `waiter-timeout` and successful `load-override` use.
- Lane reservation (v1.5): when the oldest live build waiter has passed its gate recently and no unrelated established build holds `heavy-build`, another caller may not consume its last free admitted lane. The oldest waiter proceeds; younger build waiters yield FIFO. A plain lane `take` returns 2 with `reserved for waiting build <holder>; retry or use wait-lane`; bounded lane waits keep polling. A pinned waiter reserves only its pinned lane, and lane 3 counts only while OPEN. The post-mkdir check makes simultaneous takers conservative without a new coordination lock. A waiter gate-blocked on its last three polls stops reserving until it passes the gate again. This reservation never grants a lane, evicts a holder, changes load/memory admission, or causes the waiter to hold either half while waiting.
- Lane-waiter fairness (v1.6): blocking `wait-lane` publishes the same fields and lifecycle under `lane-waiters/waiter.*`, with resource `heavy-lane-any` in waiter logs. Dead local PIDs or >45s heartbeat expiry remove priority. Among gate-ready waiters, a foreign waiting project with no non-STALE lane caps a project already holding a lane at one lane. When every waiting project already holds a lane, the oldest ready waiter may take spare capacity. A capped waiter yields FIFO position to eligible projects; it cannot deadlock their queue. A plain additional-lane take returns 2 with a project-priority explanation, and waits poll until eligible. Younger lane waiters yield to the oldest eligible waiter; other callers reserve its last free admitted lane. Build-waiter reservation is checked first, and the oldest ready blocking build waiter keeps priority over the lane queue. No live ready waiter means no cap or reservation; `res status` lists waiting lanes, including their blocker. Publication precedes the project check to cover concurrent takers. Reservations never acquire or evict a hold.
- Try: `res take <id> --by <session> --project <slug> --for "<purpose>" --task <id> [--pid <pid>]` → 0 ok, 2 held (don't block).
- Block: `res wait <id> --by <session> --project <slug> --for "<purpose>" --task <id> [--pid <pid>] --timeout <minutes>` → retries with backoff until taken (0) or timeout (2). For `heavy-*` ids, wait uses the same lane-aware gate as heavy-check with its selected holder PID on every retry; it keeps waiting while load1m exceeds the active limit or available memory is below the configured minimum (default 16 GiB).
- Lane-aware admission: full builds retain the legacy heavy gate, which counts held `heavy-lane-*` directories, including lane 3, excluding STALE holds and holds whose recorded PID equals the caller's holder PID. With no other holds it uses LOAD_LIMIT (default 12); with one or more it uses LOAD_LIMIT_WITH_LANES (default 20), always with MIN_AVAIL_GIB (default 16). Fresh lanes 1/2 instead use load1m <= LANE_LOAD_PER_CORE x physical cores (default 1.25) and LANE_MIN_AVAIL_GIB (default 12). Legacy/remote/incomplete holds remain counted unless their recorded PID equals that PID. Counted build holds do not count as lanes. No gate overrides an occupied lane.
- Gate only: `res heavy-check [--pid <pid>]` → 0 ok, 5 overloaded, 1 metrics/usage error; prints `load1m=... limit=... lanes_held=... avail=...GiB`, memorystatus percentage, page headroom, swap used, and `gate=OK|OVERLOADED`. Default PID is the caller's (`res`'s `$PPID`); wrappers pass the same `--pid $$` as take/wait. Callers using plain `take` must run this check themselves first.
- Available memory = macOS memorystatus level × RAM (`kern.memorystatus_level / 100 * hw.memsize`). Only if the memorystatus sysctl is missing, use (free + inactive + speculative) pages * page size. Page headroom and swap usage are diagnostics, not extra gates. Linux still uses MemAvailable. Invalid/unreadable metrics return 1 without acquiring a hold.
- Machine thresholds (v1.6, extended v1.8): optional `$RES_DIR/machine.conf` is plain `KEY=value` data, with blank lines, whole-line `#` comments and surrounding whitespace allowed. Supported keys/defaults are `LOAD_LIMIT=12`, `LOAD_LIMIT_WITH_LANES=20`, `MIN_AVAIL_GIB=16`, `LANE3_LOAD=8`, `LANE3_AVAIL_GIB=32`, `LANE_LOAD_PER_CORE=1.25`, `LANE_MIN_AVAIL_GIB=12`, `BUILD_LOAD_PER_CORE=1.5`, `BUILD_MAX_CONCURRENCY=2`, `BUILD_CONCURRENT_LOAD_PER_CORE=0.6`, `BUILD_CONCURRENT_MIN_AVAIL_GIB=24`, `LOAD_OVERRIDE_MINUTES=20`, and `LOAD_POLL_SECONDS=15`. Partial overrides keep remaining defaults. Values are positive decimals: load/ratios/minutes at most 1024 except override at most 1440, GiB at most 65536; concurrency is an integer 1..3 and poll seconds an integer 15..30. Held-load limit must be at least idle-load limit; lane 3 load at most idle-load limit and memory at least normal memory; concurrent ratio <= lane ratio <= first-build ratio and concurrent memory >= lane memory. Duplicate/unknown keys, unreadable files and invalid values return 1. Publish the file atomically: write the complete configuration to a temporary file in RES_DIR, terminate every record with a newline, then rename it over machine.conf. Never edit machine.conf in place; the previous file stays active while the temporary file is written. Empty, unterminated or changing snapshots are rejected before applying any overrides. Missing entries select defaults; dangling symlinks, FIFOs and other nonregular entries return 1 for heavy-check and heavy takes. The reader validates its opened descriptor as readable and regular. Configuration reads use Python 3. The controller never creates this file. Each admission reads it anew; heavy-check prints the legacy thresholds, and admission checks also print `admission-policy` with all eight v1.8 values. Configured thresholds use unrounded metrics on Darwin and Linux.
- v1.3 appends `lane3=OPEN|CLOSED` AFTER `gate=...` in Darwin and Linux heavy-check output; all previous fields and ordering remain unchanged. It describes lane-3 admission, NOT ownership/free status. An occupied lane can still report OPEN. A normal gate can be OK while lane3 is CLOSED. Both comparisons use unrounded metrics, so a displayed 8.00/32.00 can still be CLOSED. Old fixed-12 and v1.2 output remain accepted by the sampler with `lane3:null` (unknown, never OPEN).
- Lane-3 `take` checks this stricter gate itself and returns 5 when unavailable (1 for invalid/unreadable metrics). Fresh lane-1/2 takes apply the new v1.8 per-core/memory gate; waits recheck their respective gate before every acquisition and use the configured 15..30-second interval while load-blocked. Lane-3 wait treats a CLOSED lane like overload until bounded timeout (2), including if the gate closes between its check and take. Reclamation is allowed only with the lane's admission gate OPEN and age strictly >600 seconds. No existing holder is evicted if load/memory later changes; return works normally under a CLOSED gate.
- Release: `res return <id> --by <session>` on every exit path. Use a shell `trap 'res return …' EXIT`.
- Holder process (VAK addition): `take` and `wait` accept `--pid <pid>` naming the long-lived holder process; wrappers pass `--pid $$`. Default is the caller's PID (`res`'s `$PPID`), NEVER `res`'s own short-lived PID. A transient launcher exiting does not stale a hold whose recorded holder PID is still alive.
- Hold metadata: existing `by/project/task/for/since/until` keys are unchanged; new keys are `pid`, `host` (local `hostname`), and `start` (hold acquisition time, Unix epoch seconds).
- Crash/stale: take records holder PID, host and start time. STALE means the recorded PID is not alive. `res status` marks a hold STALE when the local-host PID is gone (legacy holds without PID/host and remote-host holds cannot be verified locally). `res wait`/`wait-build`/`wait-lane` auto-reclaim a STALE heavy-* hold older than 10 minutes and writes a log line. Otherwise use the existing `res return --force --note`.
- Order: full builds use `take-build`/`wait-build`, not two independent blocking waits. A private short-lived `.build-admission.lock` serializes counted-slot selection, checkout conflict checks, peak updates and release; it is never a capacity hold. Internally a short attempt takes the selected slot then a free lane using atomic mkdir arbitration; failed attempts and INT/TERM/HUP unwind in reverse. Rollback protection stays armed through cleanup and final process exit: the first cancellation is preserved even while the mkdir verdict is pending, freshly created holds are released, then that signal's 129/130/143 status is returned. A rollback helper interrupted before arming its signal shield is relaunched while its fresh directory remains. An interrupted parent wait reads the completed helper's actual verdict before retrying, so a replacement holder is not mistaken for the released attempt. Genuine cleanup errors return 1 rather than a saved cancellation status. `wait` applies the same fresh-ownership guard through its delayed PID diagnostic; an interrupted idempotent wait preserves the pre-existing hold. There is no sleep/backoff with only one capacity hold. The slot and lane directory creations are not a single filesystem transaction: observers can see a partial in-flight attempt, but contention, failure or signals return its newly created holds before waiting. SIGKILL/crash still relies on the existing STALE recovery. Never hold either capacity resource while waiting for the other.
- Holder PID: `--pid` must name the long-lived wrapper or the long-lived build process itself. Workers never take/wait for heavy locks in a standalone tool call: every tool call has a fresh shell whose `$$` exits when that call returns. Acquisition, build and return must happen in ONE process, using `scripts/heavy-build.sh <command...>` or a wrapper around `take-build`/`wait-build`.
- PID diagnostics: a dead explicit PID warns at fresh take without refusing. Fresh explicit-PID `wait`, `take-build`, `wait-build` and `wait-lane` check once after 2 seconds, after acquisition, and append `pid_warning\tshort-lived pid` if it has died. Plain `take` has no delay; idempotent takes/waits do not rewrite metadata or run the delayed check. The warning says `res: --pid <n> is not a long-lived process; pass the wrapper's $$; use scripts/heavy-build.sh <command...>`. An unavailable process probe does not establish death. A successful acquisition can include this 2-second diagnostic grace period beyond the acquisition timeout.
- Early status: a proven local dead PID with `pid_warning`, or a hold acquired within the last 5 seconds, appears as `STALE?(short-lived pid)` and prints the wrapper fix. Status remains observational. This catches a standalone tool shell that dies only AFTER res returns; a synchronous take cannot predict that later exit. Older unwarned dead holds remain `STALE`. The `?` flags suspect holder selection; the local PID is still proven dead, and the >600s reclaim rule is unchanged.
- Worker liveness: wrappers must exit when their worker dies, using exit/signal traps plus a parent watch. `scripts/heavy-build.sh --watch-pid <pid> <command...>` optionally watches a long-lived worker/follower/agent shell; disappearance terminates its owned command group and returns both holds, including while acquisition is waiting. The watched PID is distinct from the holder PID, which remains the wrapper’s `$$`.
- Same-task successor: after quota exhaustion/crash, verify the predecessor’s project/task ID, local host and dead PID in `res status` and its hold info. The successor of that task returns the predecessor’s STALE lane then slot with `res return <id> --by <predecessor-holder>`, or an explicit `--force --note "same-task takeover <task-id> from <predecessor>"` under the existing rules, then re-takes with its own unique holder and long-lived PID. A young STALE hold need not wait 10 minutes for this coordinated manual return. Never adopt unchanged PID/start metadata or return an active/unverified hold merely because its task ID matches.

## Stable State and Device Interface

Default state remains `$HOME/.claude/orchestrator/_shared`; `RES_DIR` overrides it for isolated tests.
`resources.tsv` remains five TAB-separated columns: id/kind/policy/device/description. Internal `heavy-build-2/-3` holds need no registry rows. `log.tsv`
has no header and five columns: local minute timestamp/action/id/holder/note; actions include
take/return/extend/add/note/reclaim and the three waiter lifecycle actions. `locks/<id>.d` presence is the hold; `info` retains nine
TAB-separated keys in order: by/project/task/for/since/until/pid/host/start, with optional appended pid_warning. Build holds append JSON `checkouts`, acquisition `build_mode`, `peak_concurrent`, and an internal committed marker; their return log records the final mode/peak/duration. Device holds append `adb_device_lines` (all stdout lines from `adb devices -l`, including its header and blank lines) and `device_clients` (comma-separated `PID:adb`/`PID:devicectl`, or `none`/`unknown`); the take log carries the same values. Each device snapshot probe has a two-second timeout and uses Python 3; unavailable tools or timeouts produce unknown. The client snapshots and initial explicit-PID diagnostic finish before a fresh lease directory is created, so a hang cannot leave ownership half-published. Snapshot failures never fail the take. Device serials/details and process arguments are discarded; idempotent takes retain the original evidence. No registry migration.
Live waiter records are private controller state under `build-waiters/waiter.*` and `lane-waiters/waiter.*`; callers do not create or remove them.
Status is observational, uses the same columns/notes, and does not reclaim. `until` is informational.
PID reuse counts as alive in the controller; legacy/remote metadata is not automatically reclaimed.
Same-by idempotent take never refreshes PID/start: a replacement process must return/re-take.
For an existing lane-3 hold, same-by re-take returns 0 without a new gate probe even if load/memory later closes
the gate; it does not acquire anew. New lane-3 acquisitions and bounded waits retain their admission checks.

Devices including iphone11/iphone8/s21 retain connection probes, `--offline`, ask-user/never policy,
default ask-user registration, notes and force-return coordination. `add --device -` still creates a
checkout, not a slot; the owner installs lane 3 via the reviewed registry row, not `res add`.
Legacy CLI help remains unchanged apart from the new `wait-pool` block; non-heavy command semantics and exit codes are unchanged (explicit dead-PID diagnostics also apply to take): 0 success, 2 held/timeout, 3 policy,
4 disconnected, 5 overload, 1 usage/metrics/other error. Tests never use live state or devices.

## Owner Switch

Branch -> all suites -> review -> owner switches -> dated digest notification and caller acknowledgements.
See [resources.md](resources.md#res-ownership) for source provenance, install/rollback and known pitfalls.
Do not merge over or replace the currently installed symlink target before it has been backed up.
Coordinate a quiescent switch; `--force` is an explicit owner override, never permission to kill waiters.
Stage the executable (or symlink) beside its destination and publish it by atomic rename. An in-place
copy can make a running Bash waiter read new source after it has committed a slot.

## Caller Compatibility and Observation

The public entry remains `$HOME/.claude/orchestrator/_shared/res` after the symlink switch; callers must
not use a private controller. The build wrapper's `RES_COMMAND`, env tools' `VESDK_RES_BIN`, and VAK's
`VAK_VERIFY_RES` retain their existing public-entry defaults. Existing env/VAK callers selecting only
lanes 1/2 remain compatible and need not adopt lane 3. Timeout arguments stay finite minutes (decimals
and zero allowed); pass the same long-lived `--pid $$` to heavy-check, take and wait.

The maintained `scripts/heavy-build.sh` uses `wait-build` for pair acquisition and reverse release.
v1.8 requires no caller changes: existing build/lane wrappers and finite timeouts automatically use counted capacity and the new gates; callers may pass `--checkout` to make the strongest identity explicit.
`HEAVY_BUILD_LANE` explicitly pins a lane. If unpinned lane 3 is unknown on a legacy installation, the wrapper
continues bounded waits on lanes 1/2 within the same timeout; on an exact legacy-help response from a rolled-back controller it uses zero-timeout slot/lane attempts, returning the slot before any backoff; unrelated errors still fail closed, and an explicit
missing lane-3 pin remains an error. The installer backs up code/registry, stages an idempotent lane-3 row and
publishes code before the atomic registry rename under owner quiescence, restoring both on publication failure.
The owner installs notes separately and publishes the combined rules digest with caller acknowledgements.
Rollback restores notes and the registry before switching to the printed code backup, so no old controller can
admit a registered, ungated lane 3. These two filesystem entries are not a single atomic transaction.

Telemetry recognizes an optional third lane only when observed; its absence does not make v1.2 incomplete.
`thirdLaneOnly` observations are excluded from normal-gate tuning because 8/32 admission is a distinct context.
Explicit machine.conf observations likewise stay outside default-gate tuning; their captured active
limits and memory minimum govern reader comparisons and gate diagnostics.
A captured `lane3=OPEN|CLOSED` is authoritative; legacy observations without that suffix never establish
lane-3 permission. Passive idle hints, quota-expiry preferences and utilisation reports cannot acquire,
release or modify locks, and do not change this contract's single package slot or configured machine gates.

## Fixture Tests

`node scripts/res/test/run.mjs` runs all registered res suites with scratch HOME, registry and PID probes.
