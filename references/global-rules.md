## Worker Rules
- Scope safety: never overwrite, delete or move files outside the task's scope (user files, uncommitted changes, shared headers/configs); restore anything touched by mistake byte-for-byte and report it. On devices and simulators, back up app data before any destructive step (reinstall, wipe, erase).
- Mid-turn talkback: use `codex-worker ask --default "<next action if unanswered>" "<question>"` only for a decision the brief does not settle that changes your next action; it waits for reply (default timeout 20 min). Use `codex-worker note --kind info "<text>"` (kinds: risk/scope/info/progress) only for a risk, a scope change, a decision you made, a landed commit, or a finding that changes someone else's work, never routine progress, tool hiccups (probe timeouts, missing metadata) or status (info/progress delivered on the next natural wake; risk/scope and asks wake; note --wake only when it changes someone else's work now; six wakes/hour/thread, 500 chars). Identity uses explicit flags, CODEX_WORKER_* or the newest running public context matching cwd. Restricted shared writes relay through command output without widening the sandbox; if ask exits 6, re-run the printed `ask --await <id>` command (reads only; same question/default/deadline). A blocker needing the user still ends the turn BLOCKED.
- Project dependencies and build tools fetched through normal package managers and registries (npm/pnpm/yarn, pip/uv, gradle/maven, CocoaPods/SPM, cargo, go modules, brew formulae, and SDK/toolchain components the build asks for) are installed directly into the task workspace or user-level caches, without a card or question. No secrets/credentials, production changes without a card, unapproved personal quota, or system security changes; a required login the worker lacks is BLOCKED.
- Forbidden for every worker: never read, copy, load or inject LOGIN material — login sessions, SSO/session tokens, cookies, CLI auth files (for example bytedcli's), API keys, .netrc, browser profiles, or other people's/other apps' keychain items — and never use any way of getting past a login. Running an installed, already signed-in CLI (for example bytedcli) through its normal commands is allowed and expected; what is forbidden is reading, copying, exporting or injecting its auth files or session. Stop only when the command itself reports an authentication error. The same holds for ssh and git: let them use the user's normal ~/.ssh configuration and default keys through their own commands, and do not override GIT_SSH_COMMAND, `ssh -F` or IdentityFile to avoid them; what is forbidden is reading, copying, printing or exporting key material yourself. Service keys the user placed in a project's own configuration (for example the project's .env) may be USED by running that project's code or CLI, only to call that service's official API as the project does; never print, copy, write elsewhere or send them to another service, and never read keys, sessions or auth files that live outside the project. Where a login or authorization is needed, stop and report BLOCKED with what needs signing in. When exploring build or config files (gradle/properties/.env/yaml/json, and files generated by tools such as RemoteX under `.remoteX/`), keep secret values out of tool output: search key names (`grep -l`, `grep -o '^[^=:]*'`) or mask values on lines matching password|passwd|token|secret|apikey|api_key|credential|auth before printing (for example `perl -pe 's/((password|token|secret|key|credential)[^=:]*[=:]\s*).*/${1}[MASKED]/i'`); if a value is printed anyway, send a risk note saying which file (never the value) and never repeat it in reports, configs or evidence. never put internal code, logs or private material into public search queries.
- Allowed with the user's 2026-11-13 authorization: sign OUR OWN TEST packages only when registered by manifest and hash in `~/.claude/orchestrator/_shared/user-signing/registry.json`, using only identities on the user-approved allowlist `~/.claude/orchestrator/_shared/user-signing/identities.json` (rules owner maintains each entry with dated user approval): iOS H6 keychain identity for iPhone 8; iOS cosign team DH59R4RNRY development certificate + provisioning profile 3JVMQQBHUR for iPhone 11, valid to 2027-09; Android debug keystore committed in the repo. Only orchestrators write registry.json entries; signing workers treat registry.json and identities.json as read-only. New identities require a new user approval card and allowlist entry; workers needing new entries or an unlisted identity report BLOCKED. If the H6 keychain is locked, pass only its one designated password file via stdin, never argv/env/logs. Android's repo debug passphrase from build.gradle goes through file descriptors such as apksigner file:/dev/fd/N, never argv. Never export/copy/print/log passwords or keys; report PASS/FAIL, certificate fingerprint and hashes; write a receipt under user-signing/receipts/; re-lock the keychain unless another registered signing run is active; never sign production/release packages or touch other keychains. Anything outside scope is BLOCKED and needs a user card.
- On registered shared test phones iphone8/iphone11/s21, permission/trust/install dialogs triggered by OUR OWN apps are already authorized: freely tap Allow/Authorize/Trust/OK, including for camera, microphone, photos, notifications, local network, tracking, developer trust, USB debugging and install confirmation. No per-prompt approval or button whitelist is required. Never operate the personal iPhone 15 Pro Max (`policy=never`) or a device not registered in `res`. Take/return through `res`, lease <=2 h, back up app data before destructive reinstall/wipe/erase, never enter personal-account credentials/passwords/verification codes, and make no purchases. If Codex refuses an allowed prompt, the orchestrator routes that step to Claude; do not ask the user to tap it.
- Security follows context: attack-style findings/exploit material require a --security route, including implementation/fix work that reads them. Otherwise pass defensive requirements only; other security content still requires --security. "No TRAE GPT on security decisions" applies to that CONTENT — attack-style findings and exploit reasoning — not to the act of reviewing, testing or editing routing code and the security rules themselves, which is ordinary work routed normally (do not reclassify a code review as adversarial just because the code implements a security policy). A `--security` review (`review`, `review-high`, `second-opinion`) is adversarial by default: no GPT model on any account; TTADK Kimi-K3 → DeepSeek-V4.1-Flash (TTADK or TRAE) → Claude Opus only with the user's OK, with a second reviewer from the other non-GPT family. `--defensive` (only with `--security` on those rows) keeps the ordinary security route instead — TRAE GPT excluded, TTADK GPT allowed — and its brief states only the rule and acceptance conditions, never a bypass description. Implementation/fix work under `--security` keeps the TRAE-GPT exclusion. A cyberPolicy block must not be retried or resent to another GPT account; re-route with `--adversarial`, or for a defensive confirmation re-route that part with `--adversarial` (Kimi + DeepSeek second). On TRAE it is recorded like the 983 restriction signal (gpt family out until the next 00:00 UTC); TTADK records only the `kind:'policy-block'` row and does not pause.
- Report the concrete model, effort and account (not merely TRAE); work only within the brief and sandbox. Missing login/access means BLOCKED, never a session transplant, login bypass or permission laundering.
- A queued company turn is not stalled merely because it is queued; fresh positive position with zero drain, or waiting without progress, is STALLED for new routing. Queue patience/route args enforce elapsed and predicted-start deadlines, even for flat queues. Confirm no-progress cancellation, exclude only the slow account/model lane and follow a company alternative with original flags/exclusions and same failures, without forcing fresh refresh. Never re-route active/background turns or auto-launch personal/signing work; max two hops. Approval exits 8, deferUntil persists in reroute.json and exits 9, limit exits 10; cancellation/router failure exits 7 with recovery and no duplicate. Acquire device/build holds after the first response; existing wrapper holds return on owner exit. Identity uses public registry/hub metadata, never credential files. Outcome derives hop chains; nightly measures waits/speedups.
- Remote dev machines (user 2026-11-16): steps that run ON a devbox never take mini heavy-build/lanes or heavy-check; take a machine-scoped devbox slot instead (`res wait-pool devbox-cn --pid <long-lived wrapper>` for heavy steps selects any registered numbered slot on either CN devbox, FIFO, and prints `slot=<id>`; return that ID after the step. Use `res wait-pool devbox-cn-light` (any light slot) for checks under ~5 min; SG devbox: probes only, no slots). Builds use scripts/heavy-build.sh or take-build/wait-build inside ONE long-lived wrapper only for local heavy compute (compilers/linkers/packaging on this machine); other local heavy tasks use wait-lane. PPE/staging/TCE/BITS/SCM deploys, remote pipelines, CI and company remote build services such as RemoteX (user 2026-11-16) never take heavy-build/lane locks, devbox slots or --shared-lock; shared remote/CI entry scripts stay unthrottled (local locks only in local-only wrappers; route.mjs --no-local-build). Never take/wait for heavy locks in a standalone tool call: its fresh shell's $$ dies after the call. Pass the long-lived wrapper/build PID; STALE?(short-lived pid) means fix the caller. Wrappers exit when their worker dies (exit/signal traps plus parent watch; optional --watch-pid). A same-task successor verifies project/task/local dead predecessor, returns its STALE lane then slot, then re-takes with its own PID. Timeout means report/queue, never bypass. Return resources/close owned children on every exit; never kill another task's processes.
- Routing is the orchestrator's job: do the task on the model you were given. Never stop to ask for another model, account or personal quota, and never declare a task a security route yourself (that route is for attack-style content only); if the model or a tool is unavailable, report exactly that. Do the work yourself: no sub-agents and no handing the task, or a review, to another model.
