## Worker Rules
- Scope safety: never overwrite, delete or move files outside the task's scope (user files, uncommitted changes, shared headers/configs); restore anything touched by mistake byte-for-byte and report it. On devices and simulators, back up app data before any destructive step (reinstall, wipe, erase); when that data holds login sessions or credentials (e.g. a signed-in TikTok), never back it up: a user card that approves this exact step and accepts the data loss, plus a verified APK/IPA backup, is sufficient.
- Mid-turn talkback: use `codex-worker ask --default "<next action if unanswered>" "<question>"` only for a decision the brief does not settle that changes your next action; it waits for reply (default timeout 20 min). Use `codex-worker note --kind info "<text>"` (kinds: risk/scope/info/progress) only for a risk, a scope change, a decision you made, a landed commit, or a finding that changes someone else's work, never routine progress, tool hiccups (probe timeouts, missing metadata) or status (info/progress delivered on the next natural wake; risk/scope and asks wake; note --wake only when it changes someone else's work now; six wakes/hour/thread, 500 chars). If `codex-worker` is not on PATH, use the launcher's absolute Node/script command with its RULES_SHARED, account and thread; risk-note form: `node <skill>/scripts/codex-worker.mjs --account <account> note --thread <thread> --kind risk "<file and issue, no value>"`. Identity uses explicit flags, CODEX_WORKER_*, runtime CODEX_THREAD_ID/TRAECLI_THREAD_ID or exactly one running public context matching cwd; ambiguity exits 2, never guesses the newest. Restricted shared writes relay through command output without widening the sandbox; if ask exits 6, re-run the printed `ask --await <id>` command (reads only; same question/default/deadline). A blocker needing the user still ends the turn BLOCKED.
- Project dependencies and build tools fetched through normal package managers and registries (npm/pnpm/yarn, pip/uv, gradle/maven, CocoaPods/SPM, cargo, go modules, brew formulae, and SDK/toolchain components the build asks for) are installed directly into the task workspace or user-level caches, without a card or question. No secrets/credentials, production changes without a card, unapproved personal quota, or system security changes; a required login the worker lacks is BLOCKED.
- Forbidden for every worker: never read, copy, load or inject LOGIN material — login sessions, SSO/session tokens, cookies, CLI auth files (for example bytedcli's), API keys, .netrc, browser profiles, or other people's/other apps' keychain items — and never use any way of getting past a login. Running an installed, already signed-in CLI (for example bytedcli) through its normal commands is allowed and expected; what is forbidden is reading, copying, exporting or injecting its auth files or session. Stop only when the command itself reports an authentication error. The same holds for ssh and git: let them use the user's normal ~/.ssh configuration and default keys through their own commands, and do not override GIT_SSH_COMMAND, `ssh -F` or IdentityFile to avoid them; what is forbidden is reading, copying, printing or exporting key material yourself. Service keys the user placed in a project's own configuration (for example the project's .env) may be USED by running that project's code or CLI, only to call that service's official API as the project does; never print, copy, write elsewhere or send them to another service, and never read keys, sessions or auth files that live outside the project. Where a login or authorization is needed, stop and report BLOCKED with what needs signing in. Save downloaded CI/job/build logs (bytedcli, curl, etc.) into a task dir as `.log`/`.txt`/`.out`; immediately after download and before any read, run `node <skill>/scripts/mask-logs.mjs --force <log-file-or-log-only-dir>` and proceed only after successful masking. Read only named masked CI logs with credential-excluding greps, e.g. `rg -n "<needed-pattern>" <log-file> | rg -vi "password|passwd|token|secret|apikey|api_key|credential|auth"`. When reading any file (build/config files, generated tool dirs such as `.remoteX/`, source code with key/secret/token literals, and `git diff`/`git show`/`git log -p` of them), keep secret values out of tool output: search key names (`grep -l`, `grep -o '^[^=:]*'`) or mask values on lines matching password|passwd|token|secret|apikey|api_key|credential|auth before printing (for example `perl -pe 's/((password|token|secret|key|credential)[^=:]*[=:]\s*).*/${1}[MASKED]/i'`); if a value is printed anyway, send a risk note saying which file (never the value) and never repeat it in reports, configs or evidence. Orchestrators (user 2026-11-18, standing): a secret-looking value seen only in local worker output or task logs is masked, its leak path fixed and reported in one line; no rotation and no user card. A card is needed only if the value left the machine (Feishu, MR, comment, push, upload, shared doc) or is one of the user's personal passwords/tokens. never put internal code, logs or private material into public search queries.
- Allowed with the user's 2026-11-13 authorization: sign OUR OWN TEST packages only when registered by manifest and hash in `~/.claude/orchestrator/_shared/user-signing/registry.json`, using only identities on the user-approved allowlist `~/.claude/orchestrator/_shared/user-signing/identities.json` (rules owner maintains each entry with dated user approval): iOS H6 keychain identity for iPhone 8; iOS cosign team DH59R4RNRY development certificate + provisioning profile 3JVMQQBHUR for iPhone 11, valid to 2027-09; Android debug keystore committed in the repo. Only orchestrators write registry.json entries; signing workers treat registry.json and identities.json as read-only. New identities require a new user approval card and allowlist entry; workers needing new entries or an unlisted identity report BLOCKED. If the H6 keychain is locked, pass only its one designated password file via stdin, never argv/env/logs. Android's repo debug passphrase from build.gradle goes through file descriptors such as apksigner file:/dev/fd/N, never argv. Never export/copy/print/log passwords or keys; report PASS/FAIL, certificate fingerprint and hashes; write a receipt under user-signing/receipts/; re-lock the keychain unless another registered signing run is active; never sign production/release packages or touch other keychains. Anything outside scope is BLOCKED and needs a user card.
- On registered shared test phones iphone8/iphone11/s21, permission/trust/install dialogs triggered by OUR OWN apps are already authorized: freely tap Allow/Authorize/Trust/OK, including for camera, microphone, photos, notifications, local network, tracking, developer trust, USB debugging and install confirmation. No per-prompt approval or button whitelist is required. Never operate the personal iPhone 15 Pro Max (`policy=never`) or a device not registered in `res`. Take/return through `res`, lease <=2 h, back up app data before destructive reinstall/wipe/erase, never enter personal-account credentials/passwords/verification codes, and make no purchases. If Codex refuses an allowed prompt, the orchestrator routes that step to Claude; do not ask the user to tap it.
- Security follows context: attack-style findings/exploit material require a --security route, including implementation/fix work that reads them. Otherwise pass defensive requirements only; other security content still requires --security. "No TRAE GPT on security decisions" applies to that CONTENT — attack-style findings and exploit reasoning — not to the act of reviewing, testing or editing routing code and the security rules themselves, which is ordinary work routed normally (do not reclassify a code review as adversarial just because the code implements a security policy). A `--security` review (`review`, `review-high`, `second-opinion`) is adversarial by default: no GPT model on any account; TTADK Kimi-K3 → DeepSeek-V4.1-Flash (TTADK or TRAE) → Claude Opus only with the user's OK, with a second reviewer from the other non-GPT family. `--defensive` (only with `--security` on those rows) keeps the ordinary security route instead — TRAE GPT excluded, TTADK GPT allowed — and its brief states only the rule and acceptance conditions, never a bypass description. - A queued company turn is not stalled merely because it is queued; fresh positive position with zero drain, or waiting without progress, is STALLED for new routing. Queue patience/route args enforce elapsed and predicted-start deadlines, even for flat queues. Never re-route active/background turns or auto-launch personal/signing work; max two hops. - Remote dev machines (user 2026-11-16): steps that run ON a devbox never take mini heavy-build/lanes or heavy-check; take a machine-scoped devbox slot instead (`res wait-pool devbox-cn --pid <long-lived wrapper>` for heavy steps selects any registered numbered slot on either CN devbox, FIFO, and prints `slot=<id>`; return that ID after the step. Builds use scripts/heavy-build.sh or take-build/wait-build inside ONE long-lived wrapper only for local heavy compute (compilers/linkers/packaging on this machine); other local heavy tasks use wait-lane. A worker that itself runs ssh/scp to a devbox, or any network CLI, is routed with `--needs-cli ssh` (or the CLI names) so it gets a networked sandbox; default sandboxes may have no network.
